# Thinkneering Hub - build standards

Follow this for every page, route and tool. Section A is the Cloudflare build; section B carries the DAME page and tool rules over unchanged (they describe the pages that are being ported, with their Supabase-era function names, which become routes of the same name).

# A. Cloudflare build

> Live facts (15 Oct 2026) win over any older line: domain `thinkneering.com`, D1 `thinkneering-db` with binding `DB`, no staging, Vectorize off, PBKDF2 at 100,000 iterations. Fixed on 16 Oct 2026.


## 1. Architecture

```
thinkneering.com
        |
  Cloudflare Worker "thinkneering-hub"
  |-- static assets  (public/*)          the DAME pages, unchanged
  |-- /api/rpc/<name> (worker/src/api/*)  the old database functions, now routes
  |-- auth.ts                             sessions, roles, per-tile admin, "Can edit"
  |-- ai/*                                Workers AI calls, Vectorize search, drafts
  |-- jobs.ts                             Cron Triggers: indexing, clean-up, backups
  bindings: D1 thinkneering-db (DB) | R2 hub-files (FILES) | AI | AI Gateway | Vectorize hub-vectors (VECTORS, off for now)
```

- **Live set-up (15 Oct 2026; these facts win over any older line in this doc).** Address `https://thinkneering.com` (the root domain, attached in the Worker's Domains tab; the Worker is also on `thinkneering-hub.<account>.workers.dev`). Code on GitHub (`niyaz8951/Thinkneering`), hosting on Cloudflare. D1 database `thinkneering-db`, binding `DB`; R2 bucket `hub-files`, binding `FILES`; Workers AI, binding `AI`; Vectorize is **off** (binding `VECTORS` commented out in `wrangler.toml` until the index is created; the clause search uses word overlap meanwhile). **There is no staging**: the top level of `wrangler.toml` is the live site and `env.local` is the offline copy (section 13). Deploy from the owner's laptop: `npm run deploy` (= `npx wrangler d1 migrations apply DB --remote && npx wrangler deploy`; migrations first, so a page never meets a table that is not there yet). Workers Builds can be connected later with the same two commands. Secrets: `SESSION_SECRET` (and `AI_GATEWAY_TOKEN` only if the gateway is set to authenticated), set with `wrangler secret put`, never in the repo. The repo may be private on GitHub; the static files are still treated as public. Account id and zone come from the Cloudflare login, never from the code.
- **One Worker, one `wrangler.toml`, two environments**: the top level (live) and `local` (offline, stand-in AI). A staging environment is added only when the owner asks; it would get its own D1, R2 and Vectorize.
- **Static assets** are served by the Worker's assets binding (`[assets] directory = "public"`, `html_handling = "none"` so every DAME address stays as it is), with `run_worker_first = ["/api/*", "/"]`: only API calls and the site root reach the code (the root serves `index.html`). `404.html` stays the not-found page.
- **Routing:** `POST /api/rpc/<name>` with a JSON body = the old RPC call. `api.js` posts to `/api/rpc/` + name instead of Supabase; the demo back end is gone (the local site with its seed is the demo now). Pages do not change. GET routes exist only for files (`/api/file/<key>`) and health (`/api/ping`).
- **Why the same names:** 60+ pages and scripts call `Api.*`; keeping the names means the port is server-only and every old Playwright test still runs. New routes follow the same naming (`ai_*`).

## 2. Database (D1)

- SQLite rules: `TEXT` ids (UUID v4 made in the Worker with `crypto.randomUUID()`), `TEXT` ISO timestamps (`datetime('now')` is UTC), JSON in `TEXT` columns and parsed in the Worker, booleans as `INTEGER 0/1`, foreign keys on (`PRAGMA foreign_keys = ON` is set by D1).
- **Migrations** in `db/migrations/0001_init.sql`, `0002_...`: applied with `wrangler d1 migrations apply`. A migration is never edited after it has been applied to production; a correction is a new migration. The demo users are made by `scripts/dev-seed.mjs`, run by `npm run dev` only (the reference rows - tiles, tools, products, factories, lists - are in the migration).
- **Tables** keep the DAME names (`app_users`, `app_sessions`, `app_categories`, `app_tools`, `app_user_categories`, `app_category_admins`, `app_tool_editors`, `cm_products`, `cm_factories`, `cm_runs`, `cm_run_lines`, `cm_lines`, `cm_answer_log`, `dn_map`, `dn_map_settings`, `po_values`, `po_extras`, `pr_lists`, `pr_projects`, `pr_members`, `pr_notes`, `pr_log`, `mp_maps`, `mp_nodes`, `mp_images`) plus new ones (`ai_drafts`, `ai_chats`, `ai_chat_messages`, `ai_jobs`, `app_audit`, `dn_starter_keywords`).
- **Big values out of D1:** `pr_notes.rows` live in R2 (`pr_notes.file_key`); `mp_images.data` / `thumb` are R2 objects (`file_key`, `thumb_key`); a future PDF upload is R2 too. D1 keeps the metadata and the permissions.
- **Logic moves to the Worker, not into triggers.** What `plpgsql` did (`cm__norm`, `cm__topic`, `cm__fill_structure`, `po__model`, `po__series`, `dn__product`, `pr__project`, `pr__can_share` ...) is pure TypeScript in `worker/src/lib/*.ts` (and the small `po*` helpers in `api/po.ts`), unit-tested with the same examples that were used on Postgres (FWW1600TAN -> FWW1600TA, the AHU benchmark counts, the Kifaf FCU facts).
- **Transactions:** D1 has `batch()` (atomic) but no interactive transactions. A route that writes several tables builds the statements first and sends one batch. Reads that must agree use one batch too. A conversion or upload that fails half-way removes its run row (`writeRun` in `cm.ts`); two people adding the same new clause at once are handled by one retry (`withRetry`).
- **Limits to respect:** 10 GB per database, 100 KB per SQL statement text, 100 bound parameters per statement (IN lists are chunked at 90: `chunks` / `marks` in `lib/sql.ts`), a 1 MB row is the practical ceiling (hence R2 for blobs). Bulk writes (Product Options `po_collect` with 20,000 values, `pr_submit_answers`) are chunked into batches of 500 statements.
- **Backups:** D1 Time Travel (30 days, point in time) plus a nightly Cron job (02:30 UTC) that exports every table to R2 as JSON (`backups/YYYY-MM-DD/<table>.json`, big tables in parts of 2000 rows). R2 keeps 90 days. The RUNBOOK restores from either.

## 3. Sessions, passwords, roles (`worker/src/auth.ts`)

- **Passwords:** PBKDF2-SHA256, 100,000 iterations (the most Web Crypto allows on Workers; `PBKDF2_ITERATIONS` in `lib/password.ts`; older hashes with fewer iterations are re-hashed at the next login), 16-byte salt, through Web Crypto; stored as `pbkdf2$<iter>$<salt>$<hash>`. Imported DAME users carry their old bcrypt hash (`bcrypt$...`); `bcryptjs` verifies it once at the next login and the password is re-hashed with PBKDF2. `app__check_password` rules stay (8+ characters, not only spaces).
- **Sessions:** a random 32-byte token; D1 stores only its SHA-256 hash salted with `SESSION_SECRET` (so a copy of the database alone gives no sessions, and rotating the secret signs everyone out) with user id, created and last-seen times; 12-hour life, one session per user (a new login deletes the old row, so the old tab signs out, as before). The browser keeps the token in `localStorage` and sends it in the JSON body as `p_token`, exactly as before, so `hub.js` does not change. `SESSION_EXPIRED` is still the error code pages react to.
- **Rate limiting:** the old lock-out after 5 failed attempts on the user row is there; the Cloudflare rate limiting binding on `app_login` and `app_register` (10 per minute per IP) is still to add (it needs the Paid plan's binding).
- **Roles and checks are one module:** one `Session` object per request (the user row, his tile admin rows, tile access, edit grants, the tiles and tools table, loaded in one batch) with `isAdmin`, `isSuper`, `isTileAdmin(tile)`, `canOpen(tile)`, `canEdit(toolId)`, `prAdmin`, `requireAdmin()`, `requireSuper()`, `requireEditor(toolId)`, `requirePrAdmin()`, `profile()`; `prProject`, `prCanShare` in `lib/project.ts`; `mpRights` in `api/mp.ts`. Every route calls these first; the mirror in the pages (`Hub.isAdmin`, `Hub.canEdit`) only shows or hides. The rules themselves are those of DAME standards section 1 (super user, per-tile admins, users, "Can edit", project sharing, map sharing) and do not change in the port.
- **Audit:** `app_audit` logs every admin action, every AI review batch (with the token counts) and every accept / edit / reject of an AI draft (who, when, what, before, after). Never deleted.
- **Later, if IT wants it:** Cloudflare Access in front of the site adds the company SSO without touching the code; the username login stays as the second step or is replaced then.

## 4. Files (R2)

- Bucket `hub-files`, keys by area: `notes/<project>/<note>.json`, `maps/<map>/<image>.jpg`, `maps/<map>/<image>-thumb.jpg`, `backups/...`, `uploads/<project>/<run>.pdf` (future).
- Nothing in R2 is public. `/api/file/<key>?t=<token>` checks the session and the area's permission (the project membership, the map's sharing) and streams the object. No page uses it yet (images and notes still travel through their routes as data URLs and JSON, so the pages did not change). Images are still shrunk in the browser before upload (DAME Maps rule).
- Delete rules follow the row: deleting a project, a note, a map, a branch or an image deletes its R2 keys in the same request; a Cron job to sweep orphans is still to add.

## 5. AI plumbing (`worker/src/ai/*`)

- All model calls go through AI Gateway (`env.AI.run(model, input, { gateway: { id: "hub" } })`, `AI_GATEWAY_TOKEN` added when the gateway is authenticated) so they are logged, cached and can be re-routed to another provider later without touching the site.
- Models: `@cf/baai/bge-m3` embeddings (1024 dims, stored in Vectorize index `hub-vectors`, cosine), `@cf/baai/bge-reranker-base` reranking, `@cf/meta/llama-3.1-8b-instruct-fast` (the small model) for drafting and extraction (owner, 16 Oct 2026: code compares and checks, the model only picks one of six answers from cited sources), `@cf/meta/llama-3.3-70b-instruct-fp8-fast` (large) when a rule book says `AI model: large`, and for chat later. Names and neuron rates live in one file (`worker/src/ai/models.ts`).
- Vectorize metadata on every vector: `kind` (clause, map_row, ds_row, option, project_clause), `product_id`, `factory_id`, `ref_id`; filters use these so a search is always scoped to the product and never returns rows the user may not see (the Worker re-checks every hit against D1 before showing it). Metadata indexes on `kind` and `factory_id` are created with the index (RUNBOOK section 1).
- Indexing is a job: new rows in `cm_lines` add a row to `ai_jobs`; a Cron Trigger every 5 minutes embeds pending rows in batches of 90 and upserts them; a failing batch is closed with its error (never retried in a loop). A full rebuild is `npm run reindex`, which is also the way to move to a new account. Until the index has vectors (and wherever Vectorize is absent: local, tests) the clause search falls back to word and word-pair overlap (`ai/search.ts`), with the same result shape.
- Prompts live in `worker/src/ai/prompts/*.md` with the examples they were tested on. A change to a prompt is tested against `tests/ai/golden.json` (50 clauses with agreed answers) before deployment (the golden set is still to be agreed with the owner).
- Costs: Workers AI is billed in neurons on the Paid plan; the Worker writes usage per call to `app_audit` so a monthly figure is one query. Chat and drafting are editor- or on-demand actions; nothing calls a model on page load.

## 11. Migration plan from the DAME site (Supabase + GitHub Pages)

Order chosen so the old site keeps working until the switch, and every step can be checked.

1. **Skeleton (2 days).** Repo, `wrangler.toml`, Worker with assets + `/api/ping`, D1 `0001_init.sql` (all tables, SQLite types), `auth.ts`, `app_*` routes, demo seed, `npm run dev`, Playwright login test. *(done 14 Oct 2026; live on thinkneering.com since 15 Oct 2026, no staging)*
2. **Port by family, tests first (about 3 weeks).** For each of `cm_*`, `dn_*`, `po_*`, `pr_*`, `mp_*`: port the pure logic to `lib/` with unit tests from the Postgres examples; port the routes; run the old e2e suite for that tool on `wrangler dev`. Order: `dn` + `po` (smallest), `cm`, `pr`, `mp`. `Migration-Status.md` ticks each function. *(done 14 Oct 2026)*
3. **Export and import (1 day, repeatable).** `scripts/export-supabase.mjs` dumps every table to JSON (service key, run once by the owner); `scripts/import-d1.mjs` maps types, writes blobs to R2, loads D1 in batches, queues Vectorize. Run on a local copy first (`--local`), then on the live D1 before the team moves; compare counts (users, clauses, answers, projects, notes, maps, images) with the Supabase counts, open a sample of every kind in the browser. *(scripts written and tried on a fixture; real run pending)*
4. **Parallel week.** thinkneering.com holds a fresh import; the team tries their daily work there; findings fixed. The old site stays live.
5. **Cut-over (1 evening).** Old site set read-only (a banner, `app_login` refused except the super user), final export and import, the team pointed to `thinkneering.com`, GitHub Pages site replaced by one page that points to the new address. Supabase project kept paused for 30 days, then deleted.
6. **After:** the AI roadmap (Part 3) continues on the new stack.

What changes for users: the address, and nothing else. What changes for the owner: `npm run deploy` from the laptop (or Workers Builds later) instead of a zip upload; migrations in the repo instead of re-running one SQL file; secrets in Cloudflare instead of `config.js`.

## 12. Portability for the IT team (what `RUNBOOK.md` covers)
- Move to another Cloudflare account: `wrangler login` on the new account, create D1 / R2 / Vectorize with the same binding names, `d1 execute --file` from the latest export, `r2 object put` from the key list, `npm run reindex`, set the two secrets, `wrangler deploy`, point the domain. No code change.
- Move to another domain: change the `routes` pattern in `wrangler.toml`; `SITE_NAME` if wanted.
- Export everything: `npm run export` writes D1 as SQL + JSON and lists the R2 keys; Vectorize is rebuilt from D1, never backed up.
- Rotate secrets, restore from Time Travel, read the audit log, add an admin from the command line: each is one documented command.

## 13. Rules fixed by the first delivery (14 Oct 2026)

- **Page addresses are the DAME addresses**, query strings included (`tools/projects/record.html?run=...`); nothing redirects to clean URLs. Links between pages stay relative, as they were.
- **The match key** `cm_lines.norm_hash` is the first 32 hex characters of SHA-256 of `cmNorm(text)` (`normHash` in `lib/sql.ts`); the import recomputes it from `norm_text`. `cmNorm` itself is unchanged and lives only in `lib/cm.ts`.
- **Structure of a conversion** (Part, section, place of first sighting) is worked out in the Worker from the rows of that conversion (`placeRows` in `lib/cm.ts`) when `cm_save_run` writes, first sighting wins, exactly as `cm__fill_structure` did.
- **`env.local`** in `wrangler.toml` has D1 and R2 only and `AI_FAKE = "1"`: `npm run dev:offline` and the Playwright suite run without a Cloudflare login; the AI review then uses a stand-in that marks every clause "Noted, low confidence" with a reason that says so. `npm run dev` (top-level bindings) needs `wrangler login` and calls Workers AI for real.
- **Tests:** Vitest through `@cloudflare/vitest-plugin` (vitest 4); storage is isolated per test *file*, so every test starts with `resetLogins()` (wipes the data tables, re-seeds the demo users). The `AI` and `VECTORS` bindings are removed in the test setup; AI tests inject a fake model on `env.AI`. Playwright runs against `wrangler dev --env local` and can use a pre-installed Chromium (`PW_CHROMIUM=/path/to/chrome`).
- **AI review on a project record** (owner's request, 14 Oct 2026): a button for admins of the Projects tile and the super user (`pr_run_get` returns `can_ai`, the route checks `prAdmin` itself). `ai_review_run(token, run_id, limit, replace, since)` drafts up to `limit` (max 25, the page uses 10) clauses that show no answer - no person's answer, no library answer - and the page calls it again while `remaining > 0`, passing `since` back so a "draft again" ends. For every clause: the factory's answered clauses are searched (Vectorize when indexed, else word overlap); a near-identical answered clause (>= 0.90) is copied without the model (`library-similar`, confidence high); otherwise the 70B model drafts from the three nearest library answers, their Internal Comments and the clause's Part / section (`ai/prompts/draft.md`), code maps the wording onto the six standard answers, confidence is capped at medium unless an answered library clause >= 0.6 backs it; a reply without JSON or a standard answer fails that clause only (reported, not retried in the loop). The draft is written on the record row (`cm_run_lines.compliance / remarks`, `ai_draft = 1`, `review = ''`, nobody as `answered_by`) only if the row is still the same clause and still shows no person's answer; reason, sources, confidence, model and status go to `ai_drafts`. On the page a draft is blue, says "AI draft, check it (low confidence)" with the reason on hover, has its own filter, is flagged "AI suggestion" in the Excel, and shows in focus mode. **A draft never reaches `cm_lines`, the review queue (`pr_review_list`, `cm_admin_lines.project_answers`) or another person's answer.** A person who edits or keeps a draft (record page, focus mode, section fill, Excel upload) turns it into his own answer with the usual review rules; the draft is marked accepted / edited / rejected and audited. Split / Join move drafts with their rows. `ai_review_clear` takes every draft off a record. Every batch is audited with the token counts.
- **Delivery = a zip of the repo (or a branch) with `npm test` and `npm run test:e2e` green**; `Migration-Status.md`, `AI-Roadmap.md` and this file updated.


### 13.1 Design pass (16 Oct 2026, Design brief Phase 1)

The brief's three standards (simple like WhatsApp, designed like Apple inside the DAME theme, AI engineered like Claude) override older page rules where they disagree. `docs/Screen-Map.md` lists every core screen with its one job, its one primary action and its empty state; a page is checked against it before delivery, and a new screen gets a row there first.

- **Headers** are sentence case, small and in the secondary colour: `.section-label` (13px, 600, `--text-soft`). Table heads and the phone labels of reading sheets are sentence case too. No `text-transform: uppercase`, no letter-spaced headers on any page that is touched (Product Options, Maps and Container Calculator still have some; they change when those tools are touched).
- **Figures** use tabular numbers (`.table td`, `.badge`, `.count`, `.meta`, `.small`, `.hint`, `.stat`, `.num`).
- **Numbers say what they count.** On the record: "22 of 38 clauses answered, 12 AI drafts to check, 5 waiting for review." *Answered* = a person's answer or the library's; an AI draft is never counted as answered. `pr_get` gives `drafts` per record for this (read-only count). Progress bars show answered in green and drafts in light blue (`.meter2`).
- **Loading** shows a skeleton (`Hub.skeleton(rows, { flat })`), never "Loading…" or a spinner. **Empty** lists say what is missing and offer the one button that changes it (`Hub.emptyState(host, { title, text, action })`). An error that stops a page is an empty state with one way out ("Back to Projects").
- **Phone (640px and less):** the screen's primary action is docked at the bottom (`Hub.dock([button])`, 50px high, glass bar, safe area), and the in-place copy carries `.dock-hide`. Secondary actions sit in line on a computer and behind one **More** button on a phone (`.more-items` + `Hub.more(button, [elements], title)`: an action sheet that presses the original buttons). Long filter rows wait behind a **Filters** button that shows how many are set. Tap targets 44px, inputs 16px.
- **Reasons are visible.** An AI draft shows "AI draft, <confidence> confidence — <reason>" as a line under the clause on the record (`.why`) and as a box above the answers in focus mode (`.cf-why`); the proposed answer chip is tinted, not solid, until a person owns it. Nothing relies on hover.
- **Sheets** have a grabber on a phone and close by dragging down (`Hub.dragClose(box, close)`, used by `Hub.confirm / ask / tell` and `Hub.more`); motion respects `prefers-reduced-motion`.
- **Screenshots** of the core screens at 390px and 1440px, day and night: `node scripts/screens.mjs <out-dir>` on `npm run dev:offline` (it seeds one demo project once). Before / after sheets of a delivery go in `docs/screens/compare-*.png`; the full sets stay out of git.

### 13.2 AI rules and the checks on every AI draft (16 Oct 2026)

- **What the AI review knows** besides the library comes from three places, all scoped to the record's product and factory: the clause's own `#` rules (Internal Comments: note before the first `#`, one rule per `#`), the **site rules and facts** of `ai_rules` (Compliance review > AI rules), and the **project's newest Datasheet Notes table** of the same product (rows chosen per clause, gated by section). Plain users never see `#` rules: the server sends them the note only (`noteOnly` in `ai/rules.ts`, used by `pr_run_get`, `pr_export`, `cm_save_run`).
- **AI rules** are written by the admins of the Compliance Maker tile and the super user (`requireRulesEditor` in `api/ai.ts`), not by plain "Can edit" users. Each rule: kind (rule / fact), every factory of the product or one, Part (any / 1 / 2 / 3), keywords (comma list, any one is enough, longer word forms and the subject words of `TERM_GROUPS` count), an instruction, optionally a fixed answer + remark. `ai_rules.tool` names the tool ('compliance'); another tool gets AI rules by using its own value, not a new table. Every save and delete is audited with before / after.
- **Order of a draft** (deterministic first): a >= 0.90 library answer in one of the six words, with no `#` rules on either line, is copied; else a site rule with a fixed answer and remark is applied (two rules at the same score with different answers cancel each other); else the model. Fixed-answer rules are only for narrow phrases; broad verbs ("install", "rigging") are instructions, because the same verb appears in clauses about factory-fitted parts.
- **Checks after the model** (`ai/guard.ts`, `draftAnswer`): the answer is one of the six (else one retry with the reason, then the clause is reported and left empty); a measurement in the remark that no given source contains becomes `[value]` and the draft is low confidence (the clause is not a source); a remark that repeats the answer is trimmed; hedging makes it low; Not Comply without a rule, datasheet row or library answer behind it is dropped; "high" needs a library answer (>= 0.6, same answer), a site rule with that answer, or a clause rule.
- **Versioned prompts**: `PROMPT_VERSION` / `RULE_VERSION` in `ai/draft.ts` are stored on every `ai_drafts` row; `ai/prompts/draft.md` mirrors the prompt and changes with the version string.
- **Library uploads** write the six standard answers for the known variants (`choiceOf` in `lib/cm.ts`); anything else stays as written and the result says how many were standardised.

### 13.3 The AI's evidence, maps and proposals (16 Oct 2026, evening)
- **One order of evidence** for the AI review and focus-mode proposals (`ai/evidence.ts`, `ai/draft.ts`): project datasheet by code -> library copy -> same clause in the record -> map rule with Answer + Remark -> other projects -> the model. The clause-to-row match on the server is `lib/rows.ts`, a port of `cm-rows.js` that must stay identical (parity test); a change to one is a change to both.
- **AI rules are written in Maps**, not in code and not in a table: a map is linked per product / factory in `ai_map_links`; `ai/map.ts` reads Part branches, `When / Section / Answer / Remark` special notes, the verified flag as on/off and the Settings branch. The server reads linked maps itself; Maps permissions only govern who writes them. Linking, creating and the quality figures: admins of the Compliance Maker tile and the super user.
- **Two kinds of map** (`mp_maps.kind`): knowledge and AI rule book; `ai_map_links.role` says which slot a map fills, and a link must match the map's kind. ### 13.5 Strict directions and learning from corrections (16 Oct 2026, night)

- **Citation contract** (`ai/draft.ts`, prompt `draft-2026-10-16d`). Every source shown to the model has an id: `D` datasheet row, `L` library answer, `O` Product Options, `N` AI note, `R` rule, `C` the clause's own `#` rule, (`K` knowledge branch and `F` rule-book fact until 20 Oct 2026), `M` correction, `E` earlier answer in this spec, `P` another project. The model replies `"cites": [...]`. **Comply, Comply with Remarks, Not Comply and Not Applicable must cite at least one id that is in the message**; Noted and In Contractor's Scope may cite `I` (the instructions). A reply that breaks this gets one retry; then the clause is left for a person (`NeedsSource`, counted as "left for a person", never written). The model may also decline (empty compliance) and that is a correct answer.
- **Code enforces it, not the prompt alone.** Numbers in the remark must be in a source the model *cited* (else `[value]`, low). Not Comply needs a cited datasheet row or Product Options entry, a cited answer of Not Comply, or a cited rule / note / fact saying "not offered". High confidence needs a cited library answer, rule, correction or datasheet row. The reason ends with "Used: ..." naming the cited sources.
- **Strict by default.** A Part 2 (Products) clause with no source on file and no datasheet decision does not reach the model at all (no neurons spent). Rule-book setting `Answer without a source: yes` (Decision steps > 8. AI model, special notes) relaxes this: the model may answer, always low confidence, with "no source cited" in the reason.
- **Learning from corrections.** When a person edits or replaces an AI draft, `ai_feedback` keeps both. For each new clause, the factory's 400 latest corrections are searched by similarity (>= 0.55, top 3) and shown as `[M#]` sources: "the AI answered X, a person answered Y instead". The model is told to follow the person. The nightly `learn.ts` job still writes repeated corrections (3 or more) into the rule book's Learned branch, "to verify".
- **Rule exceptions.** A rule's special note `Unless: word, word` (alias `Not when:`) stops it when the clause has any of those words; inherited down the branch like `When:`. The template uses it: Scope statements never answer a clause with shall / provide / select / submit / standard / minimum ...; Site works never answers a factory-installed item or training.

- **Reading fixes**: "not more than / no greater than / not to exceed / limited to" are maximums, "not less than" a minimum; the parent clause is found for labels stored without the full stop ("A", "1", "a"); a list item is compared with its parent's subject; units in words are read (meters per second, percent, inches, inch wg, kg/square meter, W/square meter K, degrees C, feet, pounds); "1000-Pa" reads as 1000 Pa; "vfd" no longer widens to "drive"; "END OF SECTION 237313" is not a clause; a word split at a line end ("ex-" + "ceeding") is joined without the space.

## 2e. Datasheet Notes and the row mapping

Goal: turn a product datasheet PDF into the compliance table format: Section / Component / one column per unit tag / Remarks. Admins control the rows and the wording from the website, with no code change.

**Where the mapping lives (owner's rule, 14 Oct 2026):** the row mapping is universal: one list per product, the same for every factory and every user, and it is part of **Product Options**, not of Datasheet Notes. Users see its result in Product Options; editors of Product Options maintain it there (Row mapping button on the Product Options page, `tools/product-options/mapping.html`, also reached from Admin > Products). Datasheet Notes only reads it and has no Row mapping button and no "Can edit" of its own (`app_tools.editable = false`). The same mapping drives Datasheet Notes (which rows are printed and how), the Product Options tree (which rows are collected and shown) and the project pages (Spec keywords).

- The user chooses the **Product** only; the upload appears once its row mapping has loaded. Products come from `Api.cmOptions`. There is no factory dropdown and no power supply dropdown: whatever the table shows comes from the datasheet. The **Factory** row is the first row of the table: for an AHU from the last character of the Material Name (owner's rule: `...9` = Riyadh, `...5` = Dubai, e.g. `ADN10FGW9`; `FACTORY` in `ds-parse.js`), for an FCU from the Software Name (`McQuay Smart Tools` = Shenzhen). Anything else leaves the row out and the page says so.
- **Power Supply** is read from the datasheet: the Electrical Connection printed for `Fan Supply` in "Electrical Power Inputs Data" (for example `400V/3Ph/50Hz + PE`), as printed. If there is no Fan Supply line the first line starting with "Fan" is used; if there is none the row is missing and the page says so.
- **Several units.** One PDF can hold several units (an AHU unit starts on the page with the "Unit Data" heading, an FCU unit on the page with the report title; `DSParse.parseAll` picks the reader with `DSParse.detect`), and several PDFs can be chosen at once. Every unit gets its own column headed by its unit tag (the "Unit" line of an AHU datasheet, the "Unit No." of an FCU datasheet; repeated tags get "(2)", "(3)"). Remarks is the last column. There is no "Unit" row, the tag is the column heading. A long schedule is fine: the Kifaf FCU PDF (1375 units, one per page, 26 MB) reads in about 6 s; the page shows "Reading … page n of N" while it works, the title names the first 12 units, and the Excel gets one column per unit. PDFs up to 60 MB are accepted.
- **The datasheet must match the chosen product** (`DSRead.check`): an FCU datasheet run as AHU is refused with a message naming the product to choose, on the tool and on the mapping screen, so rows never land under the wrong product's mapping.
- With one unit the Section column shows the datasheet heading (`2) Filter Supply`). With several units section numbers differ per unit, so rows are lined up by section name (a 2nd section of the same name is `Filter Supply (2)`), sub-heading and component; option lines are lined up by their text. A unit that does not have a row gets `-`. A row only a later unit has is placed after the row that comes before it in that unit. Only `DSParse.grid` builds the table.
- The PDF is read in the browser with the local pdf.js. The PDF itself is never uploaded. Saved are: the table made from it, in the chosen project (section 2i), new section and row names (row mapping below) and the values of the shown rows for the Product Options tree (section 2g; never the project, reference or unit tag). The page tells the user so.
- Readers: AHU (Daikin ASTRAWEB technical report, in `ds-parse.js`) and FCU (Daikin FAN COIL UNIT TECHNICAL REPORT from McQuay Smart Tools, in `ds-fcu.js`, built 2 Oct 2026 on the owner's Kifaf Phase-5 schedule). Chiller shows "not ready yet" until a sample datasheet is supplied; a reader registers itself in `DSParse.readers` with `starts(page)` and `parse(pages)` and is then picked up by the tool, the mapping screen and the product check.
- The reader gives: General (product, power supply, project, reference, material name, software, report date), Unit Data, then every numbered section of the datasheet in order. The Options List lines are placed under their own section (Unit Options under Unit Data). Section List, Sound Report and NRVU pages are not read; from the Electrical page only the Fan Supply connection is used.
- Labels paired with a solid dot become one row each: `Panel • Insulation` = `62 mm • Foam` gives Panel: 62 mm and Insulation: Foam. A one-word second label takes its context from the first (`Temp. Dry Bulb In • Out` gives Temp. Dry Bulb In / Temp. Dry Bulb Out). A value with dots under a single label stays as printed (`Mounting`: `Internal • Left`).
- **Differences between units.** The first unit is the reference. In every row, a cell whose text differs from the first unit's is highlighted: yellow for the first different value, then one colour per further different value (5 colours, then they repeat); equal values in a row share a colour; `-` (row missing in that unit) counts as a value. Compared after the row mapping, ignoring case and spacing (`DSParse.grid` gives `marks` per row). On screen the colours are built from the theme tokens (`--warn-bg`, `--ok-bg`, `--danger-bg`, mixes of `--brand`) and each coloured cell has a "Differs from <first unit>" tooltip; the Excel uses fixed fills (`DIFF_FILLS` in `ds-xlsx.js`). "Only rows that differ" filters the preview only; the Excel always has every row. **Same value for every unit** (owner, 21 Oct 2026): in the Excel a row whose units all show the same value (same comparison, no colour) has the value once, in the first unit's column (not wrapped, so it runs over the empty cells), the other unit cells empty, no merge (a frozen first unit column keeps it in view), and the row's unit cells framed end to end by one green line; empty rows and sub-headings are left as they are; the legend under the table says so. The screen table is unchanged.
- Two filters printed in one section are shown as Filter 1 / Filter 2. Sub-headings (Damper One Supply, Geometry, Cooling, Motor Data, Options) are shaded rows, written only when one of their rows is shown.
- **FCU reader** (`ds-fcu.js`). One page = one unit. The title block gives Project, Unit No. (column heading), Software Name + version (Selection Software) and Selection date (Report Date); two fields may share a line, so lines are cut at the field names. Headings are the bold lines alone at the left margin (bold = a font other than the page's most common one): General, Configuration information, Cooling coil (Cooling Mode), Cooling coil (Heating Mode), Electric Heater, Acoustical performance, or Sound pressure level (dB(A)) on the DC-motor layout. The rows under "General" are the **Unit Data** block; the other headings are sections without numbers (Section column shows the name as printed). Rows are printed in two columns (label | value | label | value): a label starts in a label column (left margin, or the most common start between 40 % and 60 % of the page width) and its value in the value column (the most common other start of its half), so a long label that ends a few points before its value is still split ("Shipping Dimension W*H*D (mm)" / "1841*558*250") and a split label is joined ("Running current" + "(A)"). Rows are listed column by column within a block (left column, then right), as the datasheet groups related figures by column. A label with nothing after it is a row with an empty value (the Heating Mode and Electric Heater blocks when not used). Superscripts (the tiny "3" of m³, "2" of m²) are put back into the label (`superscripts` in `ds-parse.js`, shared by all readers: only 1-2 digit tiny items raised above a line). **Power Supply** = the "Power Source" row of General, moved to the General group (not repeated under Unit Data). **Acoustic table:** the "Octave Band" row names the bands; every row under it (Lw Inlet + Rad(dB(A)), Lw Outlet Duct(dB(A)), Sound pressure level, High / Medium / Low speed) becomes a sub-heading with one row per band (63Hz … Overall), values matched to the nearest band by position; a unit printed after the last value ("dB(A)") stays with it. The "Note" lines at the foot of the page end the unit and are not read. **Factory** from the Software Name in the title block (owner's rule, 2 Oct 2026): `McQuay Smart Tools` = Shenzhen (`FACTORY` in `ds-fcu.js`); other software names are added there when the owner gives them. An unknown name leaves the Factory row out, the page says so, and those units are not collected for Product Options. Three layouts seen on the Kifaf schedule (AC 3-speed with Eurovent badge, AC with AHRI badge and a single sound-pressure row, DC 0-10V with three speed rows) all read: 1375 units, 116 distinct rows, every printed value found.
- Remarks is always empty.

**Row mapping** (`tools/product-options/mapping.html`, admins and users with "Can edit" for Product Options; the Row mapping button on the Product Options page shows for them and opens the product shown there, `?product=`):

- Kept per **product** in `dn_map` (one row per datasheet row) and `dn_map_settings`: one mapping for all factories (owner's decision, 1 Oct 2026). The first version was per factory in `dn_rules` / `dn_settings`; `schema.sql` copies those into `dn_map` once and they are no longer read or written.

Because the key uses the section name and not its number, a section that moves position keeps its mapping, and a section with a new name is added as new rows.

- The tool loads the mapping with `Api.dnRules` when the product is chosen. If it cannot be loaded, every row is shown as printed and the page says so.
- Database functions: `dn_get_rules` and `dn_add_rows` (any approved user), `dn_admin_save_rules` (editors of product-options; until 14 Oct 2026 editors of datasheet-notes, and `schema.sql` turned those grants into Product Options grants once). ## 2f. Psychrometric Chart

Goal: plot any number of air states on an ASHRAE-style chart, join them into a process, and read properties, coil loads, SHR, apparatus dew point and bypass factor. Tool id `psychrometric-chart`, General tile, no database use (states are kept in the user's browser only, and the page says so).

- **Numbers must match ASHRAE Fundamentals Chapter 1, Table 2 and Chart No. 1.** The engine (`psychro.js`) uses the Chapter 1 equations (Hyland–Wexler saturation pressure eq. 5/6, humidity ratio eq. 20, RH eq. 24, wet bulb eq. 33/35, enthalpy eq. 30, volume eq. 26, mixing eq. 45/46) **with the water-vapour enhancement factor** (Greenspan 1976 fit of Hyland–Wexler) applied to saturation pressure everywhere. Without it the results read 0.4–0.6 % low on humidity ratio, which was the original mismatch against the printed chart. Do not remove it or add a second equation set for IP; IP figures are converted at display.
- `node test-psychro.js` checks the engine against ASHRAE Table 2 (-20 to 50 °C) and Chapter 1 Example 1. Run it after any change to `psychro.js`; humidity ratio must stay within 0.05 % of Table 2.
- Chart (`chart.js`, inline SVG): dry bulb along the bottom, humidity ratio on the right, saturation curve as the clip boundary, wet-bulb lines every 1 °C with values written on the saturation curve, enthalpy every 5 kJ/kg with the scale outside the curve, RH every 10 %, specific volume every 0.01 m³/kg, SHR protractor, pressure/altitude caption on the chart. Axis numbers and anything in the margins are drawn outside the clip. Colours only through the `--chart-*` tokens defined in `styles.css` from hub tokens.
- Multiple states are the point of the tool: rows can be added, reordered, removed, picked from the chart, or produced by "Mix two states" (mass-weighted on dry air using each row's airflow; the result is stored as an ordinary row, not a live formula).
- Worked examples must be internally consistent (a "Mixed" row equals the mix of its sources). A mixed row remembers its two sources: the step into it is shown as "Mixing" with no coil load. Fan heat, reheat and heating steps keep the humidity ratio. SHR shows "—" when the total load is close to zero.
- IP mode switches the whole tool: chart axes and captions (°F, gr/lb, Btu/lb, in.Hg, ft) with round IP ticks, airflow in cfm, messages, CSV and PNG. The engine stays SI.
- Anything that changes the pressure (altitude, measured pressure) redraws the chart, the properties and the loads together.
- States are kept per user in the browser (`dame.psychro.v1:<username>`).
- State names are user text: written with `value` / `textContent` in the tables; they pass through `TN.esc` only where they enter the SVG string.

## 2h. Rules added by the user walk-through (2 Oct 2026)

Found by testing every tool as an ordinary user; list and status in the project doc `UI-Test-Findings-2026-10-02.md`.

- **Excel text is cleaned.** Anything written into an .xlsx passes a cleaner that drops characters XML does not allow (control characters, lone surrogates). Compliance Maker: `clean()` in `xlsx-writer.js`.
- **Preview and download always agree.** A setting changed after a run updates the preview at once (Compliance Maker formatting ticks) or clears the result (Datasheet Notes product change, Coil Data Extractor file list). Where the result is out of date and cannot be refreshed without a run, the downloads are disabled and the page says why (Container Calculator).
- **A failed run clears the previous result.**
- **Cut input is said clearly.** Compliance Maker: PDF 50 pages, paste 150,000 characters cut at a whole line; a warning notice above the preview and a "PARTIAL" line in the Excel band and last row.
- **Several files:** every error names its file; one bad file does not discard the good ones (Datasheet Notes shows the good units and lists the files not read).
- **No leave-page prompts** in tools. Light state (product, factory, pasted text) is kept across a reload in `sessionStorage`.
- **Work kept in the browser is per user**: storage keys end in `:<username>` (Centre of Gravity `tn.cog.v1:<username>`, Psychrometric Chart). Opening a file validates its shape before replacing anything. Replacing a non-empty list or project asks first.
- **Stored values stay in base units** (mm, kg, m³/h); unit switches convert only for display, so a round trip returns the same figures. Centre of Gravity project files are version 2 (mm and kg, display unit recorded); version 1 files still open.
- **CSV output**: UTF-8 marker, units in every heading, rounded figures; a text cell starting with `=`, `+`, `-` or `@` gets a leading apostrophe; numbers stay numbers.
- **Container Calculator.** Clearance is the gap kept between items, not to the walls; an item that fits the vehicle is never refused for clearance. Piece list, PDF and packing list show sizes as entered; positions include the clearance, and the page and PDF say so. Limit 5,000 pieces per calculation. Freight cost is empty by default with a free-text currency. "Download cargo list" gives a file the importer reads back unchanged. CSV import detects `;` and decimal commas. The PDF prints Latin text only (`[non-Latin text]` marker; the page warns; Excel keeps the text). The 45–55 % centre of gravity band is described as a rule of thumb. **Palletised cargo stays upright** (owner's rule, 2 Oct 2026): with "Cargo is palletised" ticked, "Allow turning on side" is switched off and greyed, for pallets and loose items alike (`packOptions()` in `app.js`). An item larger than every ticked pallet goes on a **made-to-size skid** (ticked by default in the pallet list: deck = the item's footprint, 150 mm high, about 20 kg per m², safe working load 2000 kg; estimates in line with the China skid presets, and the page says so), stacked up to the max load height, so it is drawn with a base like any pallet. With "Made-to-size skid" unticked such rows are packed loose and a notice in the results names them. Drawing colours follow the cargo row (`srcRow`), so they match the legend when rows are palletised.
- **Datasheet Notes.** Section and Component columns stay in view when the table scrolls sideways. Excel: fit to one page wide up to 6 unit columns, above that full size with columns A:B repeated; a legend line under the table. Difference colours repeat after 5 values and the page says so without naming a colour. FCU title block: a field name inside a line counts only when followed by a colon (or "Unit No." with its full stop). Cancel while reading.
- **Row mapping.** New rows collected from users' runs do not count as unsaved changes; Save confirms them.
- **Product Options.** Counts read "seen n times" (a datasheet run twice counts twice). A product or factory that no reader can supply says so instead of pointing to Datasheet Notes. Excel is styled by `po-xlsx.js`. An editor with Edit off sees exactly what users see.
- **Standards** (tool id `standards`, General tile, added by the owner). `Std.scan` accepts "Standard", "Std", "Guideline" and ANSI/…, BS EN ISO, ISO/IEC prefixes; a number that is not in the library is listed as "not in the library", never mapped to a neighbour; the bare word "Eurovent" is assigned by nearby product wording or listed as not in the library. `node test-standards.js` must pass after any change to `std.js` or the keys in `standards-data.js`.
- **Compliance Maker keyword rule is unchanged** (an entry word may be the start of a clause word, so `pre` also finds `pressure`); editors tighten the keyword.
- **Passwords** cannot be only spaces (`app__check_password`).
- **Admin > Users**: a row's Save is enabled only when the row differs from the stored values.

## 2i. Projects (project history and data, built 5 Oct 2026)

Goal: everything a user makes is saved against a project, can be found again, downloaded as one Excel, and seen by admins across all users. Tool id `projects`, General tile, first tile (sort 5). Files in `tools/projects/`.

- **Project** (`pr_projects`): Project name, Client type, Client name, Region. All four are mandatory (checked in `pr_save`). Client types and regions are lists in `pr_lists`, seeded in `schema.sql` (change them there). One user cannot have two projects with the same name.
- **Who sees a project:** its creator, the people it is shared with, and admins and the super user (every project of every user). Nobody else (`pr__project`).
- **Sharing** (owner's rule, 5 Oct 2026; table `pr_members`, `pr_share_get`, `pr_share_set`, **Share** button on the project page). Who may share: an admin or the super user (any project), and the project's creator **when he has "Can edit" for at least one tool** (a key user) (`pr__can_share`). A plain user cannot share his project; an admin does it for him. A project can be shared with any number of approved users (limit 200). **A member works in the project like its creator**: add specifications and datasheets, fill, upload, compare, download, change the details. A member cannot delete the project or change who it is shared with (`pr_delete` refuses). The project page shows "Shared with ..." and the Projects list marks "Shared with you"; sharing and its end are written in the project history. Ending the sharing takes the access away at once; what the member did stays in the project under his name.
- **Pages:** `index.html` (Add New Project, Project history with search and filters; admins also get creator, a summary by region / client type / product and a download of the list), `project.html?id=` (details, tool tiles, compliance records, datasheet notes, history, Download project), `record.html?run=` (one converted specification, read and filled online), `note.html?id=` (one saved datasheet table, view only), The Projects page carries the buttons **Compliance review** (editors; it opens the master library screen `tools/compliance-maker/library.html?from=projects`) and **Product Options** (everyone who has that tool); Product Options has no tile of its own (`project_tool`) and goes back to Projects (`?from=projects`).
- **One flow inside the project** (5 Oct 2026, late). The project page opens with a **Next step** card: one headline, one progress line (clauses filled of all clauses, answers in review), one button. It is worked out from what the project holds (`nextStep` in `project.html`): nothing yet = add the specification; a specification with empty clauses = continue filling it (oldest first); all filled and no datasheet of that product = read the datasheet; otherwise "Everything is filled" with the download. `pr_get` gives `clauses` and `filled` per record (filled = the project's own answer or a library answer).
- **Add a specification** (`add-spec.html?project=`): product and factory (remembered), the PDF or pasted text, "Skip the cover and contents pages", then **Convert and start filling**: the clauses are saved with `cm_save_run(..., p_project_id)` and the page goes straight to the record (`record.html`, full-screen on a phone). The conversion itself is `tools/compliance-maker/cm-engine.js` (`CMEngine.fromPdf`, `CMEngine.fromText`), **the only copy of the parser**; the classic Compliance Maker page uses the same file and is linked from Add a specification for its keyword dictionary and Excel preview.
- **Specification beside datasheet** (`compare.html?project=&product=`), offered on the project page for every product that has both. Rows = the product's row mapping; "Specification asks" = the clauses found by the row's Spec keywords (`CMRows.match`, section 2e-2) over every specification of that product in the project; then one column per unit of every saved datasheet table. A row is tied to its datasheet value by the row key saved with the table (`key` on each row since 5 Oct 2026; older tables are matched by section and component name). Rows with nothing on either side are left out; "Only rows the specification asks about" filters; Excel download. The page never judges compliance.
- **Factory options from a row** (`pr-options.js`, `PROptions.open`): pressing a row name in a saved datasheet table (`note.html`) or in the comparison opens a panel with what the factory named on the datasheet has offered for that row (the Product Options tree, `Api.poTree`), the project's own value marked "in this project", special options and notes, and a link that opens Product Options on that product, factory and row (`?product=&factory=&q=`). Read only. If the table names no factory the panel asks which one.
- **Tool tiles on the project page:** "Add a specification" (opens `add-spec.html`) and "Read a datasheet" (opens Datasheet Notes with `?project=<id>`); blue when the project holds that kind of data, grey when it holds none. A user only gets tiles for tools he has.
- **A project tool** (`app_tools.project_tool`) puts a Project select on its page and calls `PRPick.attach({ select, hint, profile, onChange })` (`tools/projects/pr-pick.js`). Nothing can be converted or read until a project is chosen; the Back button leads to the project. The choice follows `?project=` and is remembered for the tab. If the Projects tool is not live for the account, `PRPick.required()` is false and the tool works without a project, as before. A new tool that produces user output must do the same and save its output in a `pr_*` table.
- **Compliance records:** `cm_runs.project_id` (set by `cm_save_run(..., p_project_id)`). The project page groups them by product. A record is shown by its file name without the extension ("AHU Specs"); clicking it opens `record.html`: the specification as converted (black PART rows, blue section rows, Sr labels, highlights) with Compliance and Remarks boxes that save on leaving the box (`pr_run_get`, `pr_run_save_line`). A green box is the library answer; changing it makes a project answer; emptying both boxes goes back to the library answer. The spec text itself is not editable (it is the key to the library). The page downloads the styled compliance Excel (`xlsxWriter.build`, project name in the header). The user can also fill the Excel and upload it on the record ("Upload filled Excel", `pr_submit_answers`). Either way answers are stored on the record's lines (`cm_run_lines.compliance / remarks / answered_by`). An answer equal to the library answer needs nothing more; a new or different one gets `review = 'pending'`.
- **Compliance review = the master library screen** (owner's rule, 5 Oct 2026: keep the screen as it was before Projects, only reached from Projects). `library.html` is titled "Compliance review" and works as in 2d-2 (Product, Factory, To answer / Answered / All, Part, Topic, search, upload, download, conversion history). Added: filters **Client type** and **Client name** (lines met in a project of that client; lists come from the projects that used the factory), status **Filled by users, to review**, a fourth counter, a **Filled by** column, and under each clause the answers users filled in their projects (name, project, client, client type, date) with **Use this answer** / **Do not take** on the waiting ones (`pr_review_decide`). "Use this answer" writes the library answer (`answer_source = 'approved'`, logged in `cm_answer_log`); the editor can then correct the wording in the boxes as usual. A user's answer never reaches the library without this step. `cm_admin_lines` has `p_client_type`, `p_client_name`, status `review`, and returns `project_answers` per line, `client_types`, `client_names`, `counts.review` (demo mirror in `api.js`). There is no separate review page.
- **Datasheet notes:** every Datasheet Notes read saves its table (columns, rows, difference marks) in `pr_notes`, at most 12 MB per table; the page says when a table is too large. They stay in the project and never enter the compliance library. The project page shows the table online (`note.html`, with the difference colours, search, "Only rows that differ") and gives the same Excel again (`DSXlsx.build`).
- **Product options** stay one company-wide tree (section 2g), opened from the Projects page.
- **Download project (Excel)** (`pr_export`, `pr-xlsx.js`): sheets **Project Information**, then per product **Specs-<Product>** (every converted specification of that product, one under the other: Sr / Specifications / Compliance / Remarks / Answer from / Filled by, PART rows black, section rows blue) and **Notes-<Product>** (every datasheet table of that product). No Product Options or History sheet (owner's rule, 5 Oct 2026); history stays on the project page.
- **History** (`pr_log`): created, details changed, specification converted, filled compliance uploaded, datasheet notes saved, record removed, answer approved / not taken, project downloaded; each with who and when. Never deleted.

## 2j. Maps (product knowledge as a tree, built 13 Oct 2026)

Goal: a note-taking machine for product knowledge. A map is a tree (Chiller > Components > Compressor ...) that grows left to right; every branch carries notes, special notes, links and images. Tool id `maps`, **SBU tile** (sort 10), editable. Files in `tools/maps/`: `index.html`, `maps.js`, `maps.css`. No AI in the tool (owner's rule).

- **Pages.** `index.html` lists the maps the user can open, searches across all of them (`mp_search`: names, notes, special notes, image captions; plain text match) and has **Add map**. `index.html?map=<id>` is one map. `#<branch id>` shows that branch alone (the other branches disappear; the path line and **Whole map** lead back; Back works). `#at-<branch id>` opens the map with that branch selected (used by search hits and by links from another map).
- **Views.** Map (tree drawn left to right; a branch grows when clicked; the `+N` button opens and closes without selecting; arrow keys open and close) and Outline (indented list). A phone opens in Outline; the choice is kept per user (`dame.maps.view:<username>`). Open branches are kept for the tab (`dame.maps.open:<username>:<map>`). On a screen of 980px or less the Outline shows the notes of the chosen branch **under that branch**, not in a sheet; the Map view uses a bottom sheet there.
- **Read first, one Read | Edit switch** (section 2b-3). Read shows text only. Edit shows the boxes for the chosen branch: name, notes, special notes, images, links, add a branch, verify, move up / down, delete. A new map opens in Edit.
- **Special notes** are short lines (200 characters) shown as green SPECIAL chips on the branch itself, as in Product Options. Longer text belongs in the notes (8000 characters).
- **Verified / to verify.** A branch typed by hand counts as verified by its writer. **Imported branches start as "to verify"** (dashed border, counter at the top) until someone who may change the map confirms them, one branch or a branch with everything under it (`mp_node_verify`). This is how content written by Claude is kept apart from checked knowledge.
- **Import and Export are the way knowledge from Claude gets in.** Export gives a plain outline (two spaces per level, `> ` = a note line, `! ` = a special note) to copy or download; Import takes the same format, shows what it will add, and adds it under the selected branch (500 branches per import). Bullets and numbering at the start of a line are dropped; any indent width works. **The outline is text only: images and links are never imported or exported.** A round trip (export, import into a new map, export) gives the same text.
- **Images** are shrunk in the browser before they are saved (owner's rule: save database space): JPEG, 1600px on the long side at most, quality stepped down until the picture is about 450 KB or less, white behind a transparent drawing, plus a 360px thumbnail. Up to 8 on a branch and 300 on a map; a file over 25 MB or not an image is refused by name. A screenshot can be pasted (Ctrl+V) in Edit. The map loads without image data; thumbnails load when a branch is opened (`mp_node_images`), the picture when it is enlarged (`mp_image_get`). The database accepts only `data:image/jpeg;base64,...` within the size limits.
- **Links** (12 on a branch): another branch (this map or another map the writer can open), a page of the Standards tool, a tool of the site, or a web address (https, opens in a new tab). A link to a tool or standard the reader's account does not have is not shown (section 2b: never hint at tools a user cannot open). A link to a branch that was deleted is dropped at the next save.
- **Sharing is per map** (owner's choice, 13 Oct 2026): **Only me** (`private`), **Team can read** (`team_read`), **Team can edit** (`team_edit`). Team = everyone who has the Maps tool. The owner sets it in **Map settings** (name, sharing, Delete map). A team editor changes branches but cannot rename, re-share or delete the map.
- **Map managers** = the admin of the tile Maps sits on and users with "Can edit" for Maps (`app__can_edit(u, 'maps')`). They own every shared map (change, re-share, delete). **A private map is its owner's alone**, also for managers and the super user; when the owner's account is deleted, managers take it over.
- **Saving.** Typed text saves by itself 0.8 s after the typing stops and when the branch is left; one request at a time; only the changed fields are sent (`mp_node_save` takes a patch), so two people on one map do not overwrite each other's other fields. A failed save is shown in the panel with **Save again**; text typed while a save is under way is never overwritten by the reply. There is no live sync: another person's changes show after a reload.
- **Limits** (checked in the database, mirrored in the demo): map name 80, branch name 120, 2000 branches a map, 200 maps a user, 20 special notes and 12 links a branch.
- Database: tables `mp_maps`, `mp_nodes` (one row per branch; the root has no parent and carries the map name), `mp_images`. Functions: `mp_list`, `mp_create`, `mp_get`, `mp_map_save`, `mp_delete`, `mp_node_add`, `mp_node_save`, `mp_node_verify`, `mp_node_move`, `mp_node_delete`, `mp_import`, `mp_node_images`, `mp_image_get`, `mp_image_add`, `mp_image_save`, `mp_image_delete`, `mp_search`. Every one calls `mp__user` (session + the account has the Maps tool); rights come only from `mp__rights` (own / edit / read / none). The permissions block opens `mp_*` like the other parts. Demo mirror in `api.js` (`mpRights`, `mpLinks` ...; change both together).
- Not built (ask the owner first): sharing with named people, moving a branch under another branch, live sync between two people, full-size originals of images, a private note of one user on a shared branch.

- **Look and feel (design pass, 5 Oct 2026).** Clarity first, content before chrome, one clear action per screen. The rules:
  - The font is the device's own system font (`--font`: San Francisco on Apple, Segoe UI on Windows, Roboto on Android). Headings are tight and heavy (h1 30px / 700), body 15px (16px on a phone).
  - Surfaces are quiet: hairline borders, soft shadows (`--shadow`, `--shadow-lift` for things that float), radius 16px for cards, 18px for tiles, 10px for controls. The top bar is translucent glass (`--glass` + blur) and keeps clear of the notch (`env(safe-area-inset-*)`).
  - Movement is short and has a purpose: 0.2 s with `--ease`; buttons and tiles press in slightly; menus, toasts and sheets ease in. `prefers-reduced-motion` turns all of it off.
  - Tabs are a segmented control (`.tabs` / `.tab`): the chosen one is a raised chip. It scrolls sideways when it does not fit.
  - On a phone (640px and less): buttons are at least 44px high, fields are 16px text (no zoom on focus), grids are one column, a tile is a row with its icon on the left.
  - **No browser dialogs.** Use `Hub.confirm(text, { title, ok, danger })`, `Hub.ask(text, { title, hint, ok, type })` and `Hub.tell(text, { title })`; they return Promises and show a sheet (bottom of the screen on a phone, centre on a computer; Esc or a click outside cancels, Enter confirms). The title asks the question and names the thing ("Delete Tower A?"), the text says what happens, the button says the action ("Delete project"), red when it destroys something. The older Quicktools tools still use the browser's `confirm` in a few places.
  - **Dates** are written one way: `Hub.date(iso)` = 5 Oct 2026, `Hub.date(iso, true)` = 5 Oct 2026, 16:20.
- Theme switch is the sun/moon button from `Hub.themeButton()`; choice is remembered, first visit follows the PC setting.
- Font: the system stack in `--font`. Radius 16px cards, 10px controls (`--radius`, `--radius-sm`).
- Use the shared classes: `page`, `page-head`, `card`, `grid`, `tile`, `btn` (`ghost`, `danger`, `sm`), `field`, `input`, `check`, `table-wrap` + `table`, `badge`, `notice`, `tabs`, `empty`.
- Do not use the Daikin logo or trademark artwork unless the owner supplies an approved file.
