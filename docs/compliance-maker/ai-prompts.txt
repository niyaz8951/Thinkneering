================================================================================
COMPLIANCE MAKER — WHAT THE AI IS ACTUALLY TOLD
Plain-English description of every instruction the tool sends to the model.
================================================================================

There are four separate AI calls in this tool. They are described below in the
order you meet them. Nothing here is code — this is what the instructions SAY,
written out so you can judge whether they say the right thing.

Where a rule matters, the reason it exists is given underneath it. If a rule
looks wrong to you, it probably is: these were written to fit one factory's
way of working, and none of them are laws of nature.


================================================================================
CALL 1 — CLAUSE ANSWERING (the main one, "Run AI review")
================================================================================

Sent once per batch of 3 clauses. The instructions have seven parts.

--------------------------------------------------------------------------------
PART A — WHO IT IS
--------------------------------------------------------------------------------

It is told it is the compliance sheet engine for a named product built at a
named factory, and that its output goes to MEP consultants under the company's
name.

It is given a priority order, in this order:
  1. Accuracy
  2. Traceability
  3. Completeness
  4. Speed

And one sentence that overrides everything else:

  "A false 'Comply' is the most critical failure. An empty field is
   preferable to an incorrect value."

WHY: a wrong "Comply" is a commitment the factory has to honour or explain.
A blank cell is only an unfinished job. These are not the same size of
mistake, and the model is told so before it is told anything else.

--------------------------------------------------------------------------------
PART B — THE THREE-STEP LADDER
--------------------------------------------------------------------------------

It must answer each clause by working DOWN this ladder and STOPPING at the
first step that resolves it.

STEP 1 — THE SELECTION DATASHEET (highest authority)
  If a datasheet was uploaded, the fields that concern THIS clause are
  attached directly to it — not left in a list of seventeen at the top of the
  prompt for the model to search through.

  The matching is done in code, using synonym groups, so a clause about
  "casing thickness" reaches a field labelled "Panel • Insulation". Those are
  the same subject in specification English, and the model should not have to
  work that out under time pressure.

  Where both the clause and a matched field state a measurement in the same
  unit, THE COMPARISON IS COMPUTED BEFORE THE PROMPT IS SENT and written into
  it as a fact, for example:

    Clause requires 50 mm. Datasheet "Panel • Insulation" is 62 mm, which is
    GREATER than the requirement. The product's actual value is 62 mm —
    state 62 mm, never 50 mm.

  IT IS ALSO TOLD WHICH WAY IS BETTER, because knowing 62 differs from 50 is
  not enough to answer. The tool answered Not Comply on a compliant unit for
  exactly this reason: thicker insulation than asked for is a better panel,
  not a deviation.

  Each kind of value carries a direction:
    higher is better   thickness, efficiency, filter class
    lower is better    pressure drop, leakage, sound power
    must match exactly voltage, connection size
    not established    say so, and do not conclude anything from the number

  Classed values are ordered by their published scale rather than by their
  digits, because the digits disagree: TB1 is the BEST thermal bridging class
  under EN1886, while F9 is a BETTER filter than F7. A spec asking for TB3
  answered with TB2 is Comply.

  So the prompt now says, for example:

    Clause requires 50 mm. This unit is 62 mm (Unit • Panel • Insulation),
    which is greater than required, which is BETTER for panel thickness —
    the requirement is satisfied. Correct status: Comply. State 62 mm as the
    value — never 50 mm.

  WHERE THE DIRECTIONS COME FROM: built-in engineering defaults, overridable
  per product in /admin/ -> Compliance -> Comparison rules. They are shipped
  in code, unlike product facts, because thicker insulation is better wherever
  it is made and EN1886 defines TB1 as the best class for everybody. Download
  the knowledge tree to see every rule in force, defaults included.

  WHEN THE DIRECTION IS UNKNOWN the check says so and explicitly forbids
  answering Not Comply on the difference alone. An unestablished direction is
  a reason to ask, never a reason to fail a compliant unit.

  For any clause stating a requirement with a number, material, class or
  rating, it must use the matched field and compare the two technically.
    - Field satisfies the requirement -> Comply, and the remark states the
      actual value.
    - Field contradicts the requirement -> Not Comply, citing the actual value.
    - No relevant field -> go to Step 2.

  Answers from this step are marked verified: true.

  WHY IT IS FIRST: the datasheet describes the equipment actually selected for
  THIS project. Everything else describes what the factory usually does.

  If no datasheet was uploaded, it is told plainly to skip this step for every
  clause rather than being left to work it out.

STEP 2 — THE LIBRARY (past verified answers)
  Each clause arrives with up to five past answers to similar clauses, found
  by text matching before the request is sent.

  If a past answer clearly addresses the clause, it must use that status and
  follow its remark wording. There is one named special case: where a past
  answer documents an equivalent standard, the remark begins
  "Comply as equivalent."

  Answers from this step are also marked verified: true.

STEP 3 — CONSTRUCTED ANSWER (only if 1 and 2 both failed)
  It is told every clause gets an answer, and specifically NOT to fall back on
  "TO VERIFY" as a first instinct.

  It must look at how nearby and similar clauses were answered and follow that
  pattern — described as "the same way an experienced engineer would sketch a
  first-pass answer before checking it."

  Answers from this step are marked verified: false.

  THE HARD LIMIT ON THIS STEP:
    It may follow a QUALITATIVE pattern. It may NOT invent a SPECIFIC fact.

    Allowed:     "Comply — standard construction includes this feature."
    Not allowed: "Panel thickness is 1.2mm."   (a fabricated number)

    It is told never to estimate, interpolate, calculate, or use general HVAC
    knowledge to produce a NUMBER.

    If a clause can only be answered with a specific fact it does not have,
    the answer is TO VERIFY with a remark naming what is missing. This is
    described as the one remaining case where TO VERIFY is correct.

  WHY THIS SPLIT: a wrong shape of answer is recoverable by a reviewer. A
  confident fabricated number reads exactly like a real one and is not.

--------------------------------------------------------------------------------
PART C — REFERENCE DATA (from the database, never from code)
--------------------------------------------------------------------------------

Inside Step 3 it is given whatever facts are on file for this product and
factory — panel construction, filter class, fan type, and so on. These come
from the compliance_facts table and are selected per batch by relevance to the
clauses being answered.

It is told: this data was confirmed by your team, not by you; the selection
datasheet always overrides it; cite it as standard configuration; never extend
it by inference.

IF THE TABLE IS EMPTY, it is told exactly that:

  "No reference data is on file for [product] / [factory] yet. You have the
   selection datasheet and past verified answers and nothing else — do not
   state any configuration detail that neither of them supports."

WHY: an empty knowledge base should make it MORE cautious, not free to
improvise. Silence about what the factory builds is not permission to guess.

--------------------------------------------------------------------------------
PART C2 — WHAT THIS UNIT IS MADE OF
--------------------------------------------------------------------------------

A selection report lists the unit's own sections — "1) Mixing Box Supply",
"2) Filter Supply", "4) Coil Cooling DX Supply", "6) Fan Supply". That list is
read from the PDF and used twice.

FIRST, EVERY DATASHEET VALUE IS TAGGED WITH THE SECTION IT CAME FROM, and a
clause only ever sees values from the section it is about.

  This is not a refinement. The sample unit has "Tube Material • Thickness:
  Copper • 0.4 mm" on the cooling coil. A clause about CASING thickness
  matches that field on the word "thickness" alone. Untagged, the tool would
  answer a casing clause with the coil's tube gauge — a plausible number from
  the wrong part of the machine, which is worse than no answer at all.

  Whole-unit data is always available to every clause. Section data is not.

SECOND, THE MODEL IS TOLD WHICH SECTIONS THIS UNIT HAS AND WHICH IT DOES NOT:

  "The selected unit is built from these sections, in order: ...
   Sections a [product] can have but THIS unit does not: ...
   If a clause requires one of these, the selected unit does not include it.
   You may NOT answer Comply on configuration grounds. Unless a past verified
   answer shows how such a clause is normally answered, use TO VERIFY and name
   the section that is missing — the absence is a commercial question, not a
   technical one you can settle."

WHY IT STOPS SHORT OF "NOT COMPLY": a missing section usually means it was not
selected, not that the product cannot have it. That is a conversation with the
consultant, not a fact the tool should assert on its own.

Only sections an ADMIN HAS CONFIRMED are used to assert an absence. Sections
seen in a datasheet but not yet reviewed stay drafts and are never used to say
a unit is missing something — one badly parsed PDF should not be able to teach
the system that "Page 4/12" is a section of an air handler.

--------------------------------------------------------------------------------
PART C3 — WHAT THE FACTORY OFFERS
--------------------------------------------------------------------------------

Every datasheet ever read has contributed its values to a per-product list of
what this factory builds. The prompt receives it as:

  STANDARD OFFERING for AHU — what this factory builds, gathered from past
  selection reports:
  - Unit / Panel / Insulation: 62 mm Foam (standard). Also available: 42 mm Foam
  ...

WITH A DATASHEET ATTACHED it is told:

  "THE ATTACHED DATASHEET OVERRIDES ALL OF THIS. It describes the unit
   actually selected for this project; the list above is only what could be
   selected. Use it only for a property the datasheet does not state."

WITHOUT ONE:

  "No datasheet is attached, so this is your best source for what the unit
   will be. Quote the standard value. If the standard value does not meet the
   clause but a listed option does, say so and name the option — that is a
   real Comply, not a deviation. Mark these answers verified: false, because
   no project selection has confirmed them."

WHY verified: false — the value is real, but nothing has confirmed it is what
this project is buying. Orange would claim a project source that does not
exist. Amber is the honest colour.

--------------------------------------------------------------------------------
PART D — WHERE THE CLAUSE SITS
--------------------------------------------------------------------------------

Each clause is supplied with its position in the specification hierarchy, for
example: PART 2 PRODUCTS -> 2.02 CASING.

It must answer strictly in that context — a requirement under CASING is about
the casing of this product.

One line is deliberately blunt: the section path is CONTEXT ONLY, NEVER A
TECHNICAL DATA SOURCE. It cannot treat a heading as evidence.

Where the section has a learned profile (see the SOP document), that is added
too: a one-line description of what the section covers, the status most often
correct there, and how many confirmed answers that is based on.

It is also told:
  - A clause with a parent clause is a list item continuing it, and must be
    read together with its parent, never in isolation.
  - If the section path shows the clause belongs to a different discipline or
    to equipment outside this product's scope, the answer is TO VERIFY.

--------------------------------------------------------------------------------
PART D2 — WHAT KIND OF SECTION IT IS
--------------------------------------------------------------------------------

Where the clause's section has been classified from confirmed answers, one
more line is attached to the clause:

  CONTRACTOR  "This section is SITE EXECUTION work. It is not a technical
               question about the equipment: answer By Contractor with the
               fixed wording, and do not check any measurement in it against
               the datasheet."

  REFERENCE   "This section is about STANDARDS, CERTIFICATION or SUBMITTALS.
               Answer from past verified answers and reference data. A
               datasheet dimension does not answer whether something is
               certified — do not use one here."

  PRODUCT     "This section is a REQUIREMENT ABOUT THE EQUIPMENT. Check it
               against the datasheet fields for this clause first, then past
               verified answers."

Plus any note an admin has written for that section.

WHY: the datasheet and the specification are different documents. The
datasheet only ever describes the unit. The specification also covers general
standards and work in the contractor's scope, and a clause from those parts
should not be answered by looking up a number on the unit.

--------------------------------------------------------------------------------
PART E — THE FIVE ALLOWED STATUSES
--------------------------------------------------------------------------------

Exactly one of: Comply | Deviation | Not Comply | By Contractor | TO VERIFY

BY CONTRACTOR
  For any site-execution requirement — installation, erection, rigging,
  lifting, unloading, storage, positioning, alignment, anchoring, assembly,
  duct connection, electrical connection, touch-up painting, site testing,
  commissioning labour.

  The remark must be word-for-word, nothing added before or after:
    "By Contractor / Others. Daikin scope is equipment supply only."

  It must never classify these as Comply, Deviation or Not Comply.

DEVIATION and NOT COMPLY
  Allowed ONLY from Step 1 or Step 2 — never from a Step 3 guess.

  WHY: a guessed "Deviation" misrepresents what the factory actually offers,
  and a guessed "Not Comply" can lose work that was never at risk. Both are
  as damaging as a false Comply, in the other direction.

TO VERIFY
  For ambiguous wording — it is told never to interpret ambiguity — or for a
  Step 3 clause needing a specific fact it does not have.

THE RULE THAT TIES IT TOGETHER
  A Step 3 answer (verified: false) may ONLY be Comply or TO VERIFY.
  Nothing else can come from a guess.

--------------------------------------------------------------------------------
PART F — HOW THE REMARK MUST READ
--------------------------------------------------------------------------------

  - Definitive and concise. One or two sentences that close the issue.
  - Banned words: should, approximately, typically, expected, likely,
    we believe.
  - Never mention internal catalogues, datasheets, selection reports or file
    names. State the value, not the document it came from.
  - Follow the wording of the past verified answers closely.

  - NEVER REPEAT A MEASUREMENT FROM THE CLAUSE AS THE PRODUCT'S VALUE. The
    clause states what is REQUIRED. Only a datasheet field or a past verified
    answer states what the product IS. If the clause asks for 50 mm and the
    datasheet says 62 mm, the answer says 62 mm. If the clause asks for 50 mm
    and no source states a thickness at all, the thickness is unknown — that
    is TO VERIFY, not "50 mm".

WHY THE BANNED WORDS: a consultant reads hedging as an unanswered question.
WHY NO FILE NAMES: the matrix is an external document; internal references
leak process detail and invite questions nobody wants to answer.

--------------------------------------------------------------------------------
PART G — WORKED EXAMPLES
--------------------------------------------------------------------------------

Five patterns are shown, covering: a datasheet-backed value, equivalency, the
fixed By Contractor wording, a qualitative Step 3 answer, and a legitimate
TO VERIFY.

EVERY ONE OF THEM IS MISSING ITS ACTUAL VALUES ON PURPOSE, marked with
[square brackets]. They used to carry real numbers and brand names, and the
model copied them onto unrelated clauses — see check 2 below. Concrete
examples teach a small model the content, not just the shape.

Two BAD examples are shown explicitly:
  - A remark that just repeats the status word ("TO VERIFY" / "TO VERIFY").
  - A fabricated number presented under verified: false.

Then the output format: a JSON array, one object per clause, in the same
order, with no commentary around it.


================================================================================
CALL 2 — THE FALLBACK PROMPT (when Call 1 comes back empty)
================================================================================

Roughly six lines. Everything optional is stripped: no priority ladder, no
worked examples, no reference data.

It says: you write compliance matrix answers for this product from this
factory; for each clause give a status and a short remark; the status must be
one of the five; mark verified true only if a datasheet field or past answer
supports it; if unsure use TO VERIFY and say what is missing; never leave the
array empty; return exactly N objects as JSON.

WHY IT EXISTS: a small model under a JSON grammar sometimes satisfies the
format with an EMPTY array. That is not a refusal — it is the model running
out of room to think while the grammar still forces well-formed output, and it
gets likelier the longer the prompt is. Length is the lever, so the retry is
short on purpose.

If this also comes back empty, the same short prompt is sent one clause at a
time, which nearly always lands.


================================================================================
CALL 3 — DATASHEET FIELD EXTRACTION
================================================================================

Runs when a selection datasheet PDF is uploaded, after a pattern-matching pass
has already pulled out whatever it recognises.

The model is given the datasheet text and asked to return Label: Value pairs
for the equipment's configuration — panel construction, coil, fan, filter,
controls, and similar. It is told to report only values present in the text.

The results are merged with the pattern pass. Pattern matches win on conflict,
because they are literal text extraction and the model's are interpretation.

WHY BOTH: patterns are exact but only find labels somebody thought to list.
The model finds labels nobody anticipated but occasionally reads a table
column wrong. Running both and preferring the literal one gets the coverage
without the interpretation risk.


================================================================================
CALL 4 — SECTION DESCRIPTIONS ("Write missing summaries" in /admin/)
================================================================================

Runs only when an admin presses the button, on at most 15 sections per press.

For each section it is given the section heading and up to six real clauses
from it, and asked for ONE sentence under 25 words saying what the section
covers for this product. It is told to describe only what the clauses show,
with no preamble and no quotes.

That sentence is then supplied to Call 1 for every future clause in that
section (Part D above).

WHY IT IS SEPARATE AND MANUAL: this writes into the knowledge base, which
affects everyone. It should be a decision, not a side effect. And an admin
who edits a summary by hand LOCKS it — a later rebuild will not overwrite a
human description with a machine one.


================================================================================
THE CHECKS THAT RUN AFTER THE MODEL ANSWERS
================================================================================

Instructions are not enforcement. Every answer is inspected before it is
shown, logged, or exported, and withdrawn if it fails any of five checks.

ONE PRINCIPLE BEHIND ALL FOUR: a remark may only contain what a source
actually said. An answer that cannot be traced is withdrawn rather than shown.
A blank row costs a few minutes of someone's time. A confident wrong answer
costs a commitment nobody agreed to.

  1. UNFILLED TEMPLATE
     The remark still contains a [placeholder] from the example patterns.

  2. REPEATED EXAMPLE
     The remark reproduces wording from an example, on a clause it does not
     fit. This is not hypothetical: a casing thickness clause came back
     answered "Comply as equivalent. Daikin AHUs comply with EUROVENT
     standards", and an insulation clause came back with "0.7mm galvanized
     outer skin, 42mm PU foam insulation" — both were example text, word for
     word, on the wrong clauses. The examples no longer contain real values,
     and anything matching one is discarded.

     The By Contractor sentence is exempt. That one is meant to be exact.

  3. UNSOURCED MEASUREMENT
     The remark quotes a measurement that no datasheet field and no past
     answer provides. This covers both ways it goes wrong: restating the
     clause's own requirement as the product's value, and inventing a value
     outright.

     Only numbers carrying a unit are checked (mm, kg, kW, Pa, %). Bare
     numbers are ignored deliberately: "AHRI 430" and "Section 237313" are
     references, and repeating them is correct.

  4. ANSWER CONTRADICTS THE COMPUTED COMPARISON
     The comparison already concluded the requirement was satisfied and the
     answer says Not Comply, or it concluded the opposite and the answer says
     Comply. Caught in both directions, though they are not equally costly:
     a false Comply is a commitment nobody agreed to.

  5. EVIDENCE IGNORED
     The datasheet supplied a value in the same unit the clause asks about,
     and the answer did not address it — answering a thickness clause by
     talking about certification, for instance. The withdrawal names the
     value that should have been used.

The count of withdrawn answers is reported in the status line after every run
rather than hidden. A rising count means the datasheet is not being read well,
which is something you want to know.

WHY CHECKS AND NOT BETTER INSTRUCTIONS: the prompt has forbidden invented
numbers from the beginning, and said "do not reuse this content" directly
above the examples the model then reused. A small model parrots concrete text
regardless of what the surrounding sentence says. An instruction is a request;
a check is a guarantee.

WHY A CHECK AND NOT JUST A BETTER INSTRUCTION: the prompt has forbidden
invented numbers from the beginning, and the model did it anyway. An
instruction is a request. A check is a guarantee.


================================================================================
THINGS WORTH ARGUING WITH
================================================================================

These are judgement calls, not facts. Each is a reasonable place to disagree.

1. BATCH SIZE IS 3 CLAUSES.
   Small batches keep the prompt short and reduce empty responses, but cost
   more calls per matrix. If empty batches have stopped happening, raising
   this is the cheapest speed win available.

2. STEP 3 EXISTS AT ALL.
   The tool deliberately produces a guess rather than leaving a blank, on the
   theory that a marked starting point beats an empty cell. If your reviewers
   would rather see blanks, this step could be removed entirely and the model
   told to answer only from Steps 1 and 2.

3. FIVE PAST ANSWERS PER CLAUSE.
   More context usually means better answers, up to the point where prompt
   length starts causing empty responses. This number was set for safety, not
   measured.

4. THE BY CONTRACTOR WORDING IS FIXED VERBATIM.
   Good for consistency, and it means that remark can never drift. But it also
   means changing that sentence requires a code change, not a database edit.

5. THE SYNONYM GROUPS ARE IN CODE, NOT THE DATABASE.
   "Casing = panel = skin" is a property of specification English, not of any
   factory, which is why it did not go in with the product facts. But it is
   still a list somebody has to maintain, and a missing group means a
   datasheet field silently fails to reach the clause that needed it. If you
   find yourself wanting to edit it often, it should move to the database.

6. TEMPERATURE IS 0.1.
   Nearly deterministic. Same clause, same answer. If answers feel rigid or
   repetitive across different phrasings of the same requirement, this is the
   dial.
