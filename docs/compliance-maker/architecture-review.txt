================================================================================
COMPLIANCE MAKER — ARCHITECTURE REVIEW AND REDESIGN
Written after measuring a real completed matrix (Al Bustan, 585 clause rows).
================================================================================

This document says what is wrong with the current build, what the evidence
says, and what should replace it. It is deliberately blunt. Nothing here is
about the quality of individual answers; the problem is one level up.


================================================================================
1. HOW WE GOT HERE
================================================================================

The tool was built reactively. Each problem produced a patch:

  wrong number quoted        -> add a guard
  empty model response       -> add a retry pass
  wrong section's value used -> add a table
  wrong comparison direction -> add another table
  copied example text        -> add another guard

The result is ten knowledge tables, five post-answer guards, a three-pass
retry ladder, eight stacked prompt blocks and a dual-write migration. Each
piece was a correct response to a real failure. Together they are the shape of
debugging, not of design.

The deeper problem: none of it was ever measured. Every change was justified
by a screenshot and shipped on faith. A team that does this professionally
would have had a scored regression set before the second change.


================================================================================
2. WHAT THE EVIDENCE ACTUALLY SAYS
================================================================================

Measured on one real completed matrix, 585 clause rows:

  Rows a human ANSWERED                         124   (21%)
  Rows a human LEFT BLANK                       461   (79%)
  Answered rows that got a REMARK                47   (37% of answered)

  THE TOOL ANSWERS EVERY BLANK ROW.

So on this document the tool produces roughly 585 statuses and 585 remarks
where a human produced 124 and 47. That is about TWELVE TIMES the text, and
every extra line is something an engineer has to read and delete before
sending. This — not per-answer accuracy — is the reason the output feels
unusable. An answer that is 90% accurate but should not exist is not 90%
useful; it is negative.

Of the 123 answers a human did write:

  scope rule (By Contractor)         14   deterministic
  informational (Noted)               3   deterministic
  bare status, no remark             42   deterministic
  pointer remark ("refer report")     7   template
  ------------------------------------------------------------------
  NEEDS NO LANGUAGE MODEL AT ALL     66   (53%)

  states our value + comparison       6   ( 4%)  KB lookup, then compare
  not applicable to this selection   24   (19%)  needs product knowledge
  free-text judgement                27   (22%)  genuinely needs language

Two things follow.

FIRST: over half of the real work needs no AI. The system was built AI-first
and everything else was bolted around it. That is backwards.

SECOND: the entire comparison engine — direction rules, class scales, the
62 mm/50 mm logic, three of the five guards — serves SIX ROWS out of 585. It
is not wrong, and it should stay, but it consumed most of the build effort for
1% of the document. That is a straightforward misallocation, and it happened
because it was the failure visible in a screenshot.


================================================================================
3. THE IDEA THAT DOES NOT WORK
================================================================================

The obvious fix is to teach the tool to answer fewer rows. It was tested
before being proposed:

  a linguistic rule (does the clause make a demand — shall, provide,
  minimum, certified — and is it not a bare header)

  precision 22%   recall 22%   F1 22%
  answering every row, for comparison:  precision 21%

Indistinguishable. WHICH ROWS DESERVE AN ANSWER IS NOT PREDICTABLE FROM THE
CLAUSE TEXT. It is judgement about what a particular consultant on a
particular project will scrutinise, and two competent engineers would produce
different sets.

That kills answer-selection as a text classification problem, and points
somewhere better.


================================================================================
4. WHAT SHOULD REPLACE IT
================================================================================

Specifications are boilerplate. The same clauses recur across projects, often
word for word, and the same firm answers them the same way. The valuable asset
is not the model — it is the accumulated record of what this team decided last
time, INCLUDING what they chose not to answer.

So the system should be RETRIEVAL-FIRST and generation-last.

  STAGE 1  RECALL
    Match each clause against every previous decision on that clause.
    Confident match -> reproduce the previous decision exactly, including
    "leave blank". No model involved. This should carry most of a repeat
    specification.

  STAGE 2  RESOLVE (deterministic)
    For clauses with a requirement the knowledge base covers, look up what we
    offer and compare with the direction rules. Produces status and value
    without a model, and cannot hallucinate because nothing is generated.

  STAGE 3  DECIDE (deterministic)
    Status from the comparison. Remark from a template learned from the answer
    corpus ("Offered units are with {value}"). Still no model.

  STAGE 4  GENERATE (model, narrow)
    Only clauses that reached here — genuinely novel, genuinely needing
    language. One clause at a time, structured output, small prompt.

  STAGE 5  ABSTAIN
    Anything Stage 4 cannot ground: leave blank. Silence is the correct output
    79% of the time, and a blank row costs a few minutes where a confident
    wrong row costs a commitment.

The guard layer largely dissolves. Guards exist because a model generates
answers it cannot support; when the answer is computed from a database row,
there is nothing to fabricate. Guards remain only on Stage 4 output.

WHAT CHANGES IN PRACTICE
  - The model handles maybe a fifth of rows instead of all of them. Cheaper,
    faster, and the failure modes shrink with the surface area.
  - Reliability comes from the corpus growing, not from prompt tuning.
  - The 62 mm comparison work stays, correctly scoped to the few rows it
    serves.


================================================================================
5. WHAT HAS TO EXIST BEFORE ANY OF IT
================================================================================

A SCORED REGRESSION SET. Your completed matrices are it: each one is 585 rows
of ground truth covering row selection, status and remark. Three numbers,
tracked on every change:

  ROW SELECTION F1   did we answer the rows a human answered
  STATUS ACCURACY    on rows both answered, did the status match
  REMARK USEFULNESS  was the remark kept, edited, or replaced

Without these, every future change is another screenshot-driven patch, and
this document will need writing again in a month. With them, "does this help"
stops being a matter of opinion.

Build order:
  1. Eval harness over uploaded completed matrices.       (measure)
  2. Stage 1 recall, including blank decisions.           (biggest win)
  3. Route Stage 4 to only what 1-3 could not answer.     (shrink the model)
  4. Retire the dual-written legacy tables.               (tidy)


================================================================================
6. WHAT WAS CHANGED NOW
================================================================================

One change, because it is a prerequisite for Stage 1 and cannot be recovered
retroactively:

  BLANK ROWS ARE NOW RECORDED AS DECISIONS.

Previously an uploaded matrix contributed only its answered rows, and the 79%
a human deliberately skipped were discarded. Nothing in the system could ever
learn what not to answer. Blanks are now stored with verdict 'blank' — kept
out of the answer log, since a blank is not an answer to pre-fill, and kept in
the feedback record where row selection can be learned from them.

Every matrix uploaded from today builds that corpus. Ones uploaded earlier
cannot be recovered, which is why this went in ahead of the rest.


================================================================================
7. WHAT I WOULD NOT DO
================================================================================

Rewrite it all in one pass. That is how the current state came about — a large
change with no measurement, justified by confidence. The eval harness comes
first, then Stage 1, and each step gets judged against the numbers rather than
against a screenshot.
